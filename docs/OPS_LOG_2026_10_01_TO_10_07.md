## 5. MouseMine 1.8 lock-ups (Oct 4–5)

- **Symptoms:**
  - Public MouseMine returned 504 from **04:27 UTC Oct 4 (about 33 h)**, then again twice on Oct 5.
  - The container stayed "Up", and Docker never restarted it.
- **Not memory:** a thread dump showed all 200 Tomcat threads in `XMLValidator.validate`. Every API query makes
  MouseMine 1.x fetch its own `query.xsd` over HTTP (`webapp.baseurl`).
- **The flood:** a scraper, about 79K IPs with a desktop-Chrome UA, sent 200–400K requests an hour. It filled all
  threads, so the self-requests could never be served: a deadlock with CPU idle.
- **Fixes, inside the container** (they persist across restarts, **not** across a container recreate):
  - `conf/server.xml`: a private connector `127.0.0.1:8081` with its own 50 threads.
  - `webapp.baseurl=http://localhost:8081` in `WEB-INF/web.properties` and `classes/intermine.properties`
    (backups `*.bak-pre-8081`).
  - `bin/setenv.sh`: `-Xmx10g` (container limit 8 → 14 GB via `docker update`), plus
    `-Dsun.net.client.defaultConnectTimeout=5000 -Dsun.net.client.defaultReadTimeout=15000`.
  - Result: 0.2 s responses under the full flood; 87K self-fetches via 8081; no stuck threads.
- **Watchdog:** `scripts/mine-watchdog.sh` + `install_mine_watchdog.sh` (f4523e0).
  - A `mine-watchdog.timer` checks every minute.
  - It restarts `mousemine-1x` after 5 failed `/service/version` checks (15 min cooldown, at most 4 per 6 h),
    then warms the keyword search.
  - Log: `journalctl -t mine-watchdog`.
- **WAF (Chris):** `alliancemine-intermine-bot-control` covered only the AllianceMine, WormMine and BlueGenes hosts.
  - It now covers MouseMine too: shared throttling of expensive API queries, browser challenges on report pages,
    and verified crawlers exempt.
  - Allowed query traffic fell from 6,600–8,000/min to 7–120/min.
  - FlyMine and YeastMine hosts are still not in it.

## 9. WormMine (Oct 7)

- **The alarm:** the 5XX alarm fired repeatedly. About 95% came from WormMine: 80–160 an hour, up from 5–40 a day
  before Sep 30.
- **Two causes:**
  - A crawler requesting about 22K `sequenceExporter.do` links a day with expired session IDs
    ("Session already invalidated"). Harmless.
  - A **data bug**: **885,206 sequence features** (34,759 *C. elegans* genes and features of every species) point at
    SOTerm **`24000006`**, which doesn't exist.
- **How the term went missing:**
  - `wb-acedb-gene` created a `gene` SO term (24000006).
  - Later `go-annotation` / `celegans-gff3` / `panther` created another (4000029).
  - An equivalent-object merge kept 4000029 and deleted 24000006 without repointing references.
  - The build never loads the SO ontology: only 29 SOTerms, none with an identifier.
- **Impact:**
  - Queries including `sequenceOntologyTerm` **silently dropped those features** (inner join to nothing).
  - Some report pages threw NullPointerException.
- **Fix (in place):** `~/ops-scripts/wormmine_fix_soterm.sh` recreated 24000006 as a copy of 4000029
  (3 rows: `intermineobject`, `ontologyterm`, `soterm`; one transaction), then `docker restart wormmine`.
  - mig-36 / T24E12.15 now return their type; 49,164 *C. elegans* genes typed `gene`; the failing pages load.
  - No reindex needed: no existing object or ID changed, there are no precomputed tables, and search is unchanged.
  - Undo: delete id 24000006 from those 3 tables. The pre-fix state is also in the RDS snapshot
    `rds:intermine-postgres-2026-10-07-03-16`.
- **Next WormMine build:** load the `so` source (SO terms with identifiers merge correctly). Check for other dangling
  references the same merge pattern may have left.

## 11b. MouseMine lock-up caused by the backup dump (Oct 7, 15:14-15:23 UTC)

- **What happened:** MouseMine drained from ~2,400 requests/min to 0 between 15:14 and 15:18. The watchdog restarted it
  at 15:22:37 (back 15:23:54); the alarm emailed and cleared at 15:27. About 6 minutes of impact.
- **Cause:** the S3 dump of `mousemine_rc4` started at 15:13. `pg_dump` holds a lock on every table for the whole
  dump, and MouseMine constantly drops temporary list tables (`DROP TABLE Integer_bag_<n>`). Each drop waited behind the
  dump's lock while holding a database connection, until all 20 were taken.
- **Fix:** stopped that dump (the script deleted the partial upload and moved on).
- **Lesson:** **do not `pg_dump` a live 1.x InterMine database while it serves traffic.** Back up `mousemine_rc4` from a
  restored RDS snapshot instead (restore to a temporary instance, dump it, delete it). The `mousemine_im5_test` dump
  is fine (not public).
- **Related:** with `os.query.max-time` raised to 500M, MouseMine no longer refuses very expensive queries, and four
  `COUNT(*)` queries ran 20+ minutes holding pool connections. Added
  `ALTER DATABASE mousemine_rc4 SET statement_timeout = '5min'`, which matches the load balancer's 300 s. It applies
  to new connections; the pool cycles them within about 30 min.

## 11c. RDS at 100% CPU for ~15 h after the query-limit raise (Oct 7 16:00 – Oct 8 07:00 UTC)

- **What happened:** the `RDS-intermine-postgres-CPU-Critical` alarm fired at 16:01 UTC Oct 7 and cleared at
  07:30 UTC Oct 8.
- **Cause:** the 5.1 test DB dump ran until 18:44, but CPU stayed pinned for 12 more hours. Raising
  `os.query.max-time` to 500M on AllianceMine and MouseMine lets queries both used to refuse actually run.
  - AllianceMine had **no** statement timeout.
  - MouseMine's 5-minute timeout (§11b) applies only to new connections, and InterMine's pool kept connections
    up to 21 h old.
- **Fix (Oct 8):**
  - `ALTER DATABASE alliancemine_9_1_0_rc1 SET statement_timeout = '5min'` (its pool recycles every 30 min).
  - Restarted `mousemine-1x` so all its connections carry the timeout.
  - WormMine already had 10 min; FlyMine and YeastMine have none, and still use lower query limits.
- **Rule:** raising `os.query.max-time` must come with a database `statement_timeout`.

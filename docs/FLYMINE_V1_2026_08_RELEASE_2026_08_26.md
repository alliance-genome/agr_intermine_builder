## Build sequence (dev host `172.31.60.197`, `/home/ec2-user/flymine-deploy/`)

1. **Image rebuild** — the deployed `flymine-builder` was 2 months stale and
   **missing the current `finalize_build.sh` + `gen_objectstoresummary.py` +
   `patch_intermineobject_blob.sql`** (same stale-image trap as the AllianceMine
   9.1.0 build). Rebuilt from the synced `docker/flymine` context. **Always
   rebuild the image before a release** or the WAR ships without the
   objectstoresummary injection + blob patches.
2. **Chado FB2026_02 restore** — dropped the old 109 GB `chado-pg-data` volume,
   restored `FB2026_02.sql.gz` (16.4 GB gz from `s3ftp.flybase.org/releases/FB2026_02/psql/`)
   into a fresh `chado-pg`. Result: 157 GB, **98,008,300 features**.
3. **Data fetch** — `extract_data.py --all` (`FB_RELEASE=FB2026_02`): 65 GB
   (flybase 18G, ncbi 14G, interpro 13G, psi 12G, uniprot 9.3G).
4. **Data-fix pass** (`fix_flymine_data.sh`, see §Data fixes) — the fetch left
   several sources' data in the wrong layout or missing; fixed before integrating.
5. **buildDB** → **25-source integration** (project.xml order, drosophila-homology
   excluded) → all **25/25 OK**.
6. **postprocess** (15 steps) → **finalize** (SQL patches → summariseObjectStore
   → WAR → objectstoresummary injection + CDN patch).
7. **Cutover** — see §Cutover.

`RC_NUMBER=1` is pinned in `.env`. **Guard:** `run_builddb.sh` aborts if
`db.production.datasource.databaseName` isn't the intended `flymine_v1-2026-08_rc1`
(the rc18-wipe lesson) — it caught an unintended rc2 auto-increment on the first run.

## Data fixes (`fix_flymine_data.sh`)

`extract_data.py --all` fetched the data but 12 sources failed the first
integration pass. Root causes and fixes (all URLs verified 200 before use):

| Source(s) | Cause | Fix |
|---|---|---|
| flybase-allele-descriptions, flybase-transgenic-constructs | source wants `<dir>/current/`, files landed in `<dir>/` | `current -> .` self-symlink |
| flybase-allele-stubs | wants `alleles/aux/current/fbal_to_fbgn_*.tsv` | **real copy** into `aux/current/` (an absolute symlink to the host path is a dangling link *inside the container* — `/root/data` ≠ host path) |
| flybase-dmel-{gene,cds,5primeUTR,3primeUTR}-fasta | no `flybase/fasta/` dir at all | fetch the 4 `dmel-all-*-r6.68.fasta` from `s3ftp.flybase.org/releases/FB2026_02/dmel_r6.68/fasta/` |
| uniprot-fasta | truncated `.part` download | fetch `uniprot_sprot_varsplic.fasta.gz` |
| uniprot-keywords | `keywlist.xml` was gzip mis-named `.xml` | re-fetch `keywlist.xml.gz` + gunzip |
| interpro-go | empty `interpro/ontology/current/` | fetch EBI `interpro2go` |
| update-data-sources | missing `uniprot/xrefs/current/dbxref.txt` | fetch UniProt `dbxref.txt` |
| do, go, go-annotation | FMS ontology/GAF files absent (FMS snapshot API returned empty JSON) | **copied `ONTOLOGY_GO/DOID/SO.obo` + `GAF_FB.gaf` from the AllianceMine 9.1.0 build** (same Alliance-wide files) |

## The objectstoresummary fix (the error in the release screenshot)

rc3 was live showing on `begin.do`:
```
Problems finding objectstoresummary.properties file.
Unable to load objectstoresummary.properties file.
Unable to find the class count. cannot find class count for: org.intermine.model.InterMineObject
```

**Root cause:** InterMine's `:webapp:summariseObjectStore` silently fails on the
`Sequence.residues` Clob and produces no summary; the AGR pipeline falls back to
`gen_objectstoresummary.py`. rc3's deployed WAR had **no `objectstoresummary.properties`
at all** (at either `WEB-INF/` or `WEB-INF/classes/`), so the page errored.

**Key format is NOT the bug** — the *working* AllianceMine rc20 uses the same
`.classCount` keys (e.g. `org.intermine.model.InterMineObject.classCount=…`), loaded
from **`WEB-INF/objectstoresummary.properties`** (no `classes/` copy). The bug was
purely the *missing file*.

**Fix:** the rebuilt image's `finalize_build.sh` injects
`gen_objectstoresummary.py`'s output (106 class counts + `InterMineObject.classCount`)
into `WEB-INF/objectstoresummary.properties`. The v1-2026-08 WAR has it; the error
is gone. Verified: `begin.do` clean, page shows `v1-2026-08`.

**Known limitation:** this is the class-count-only summary (106 lines) — enough to
render pages and clear the error. The richer field-value summaries (query-builder
dropdown suggestions, ~2100 lines on a full summary) still need
`summariseObjectStore` to stop failing on `Sequence.residues`. Follow-up, not a blocker.

## Cutover — why file-swap, not cargo

FlyMine is deployed as a **read-only bind-mounted WAR**:
`/home/ec2-user/mine-wars/flymine.war -> …/webapps/flymine.war (RW=false)`.
This is the reboot-resilience fix from `INCIDENT_MULTITENANT_REBOOT_2026_06_23.md`
(the WAR used to live in `/tmp` and vanished on reboot).

`cargoRedeployRemote` deploys by PUTting the WAR through the Tomcat manager, which
makes Tomcat **write** `webapps/flymine.war` — that write fails against the RO mount
(and undeploy would fail deleting it). The manager *is* up (401, reachable), but the
architecture is deliberately file-swap, not cargo. Using cargo would mean recreating
the container without the persistent mount — regressing the reboot fix.

**Clean approach used:** rebuild the WAR with production pointers **baked via env**
(the properties template resolves `db.production`, `db.userprofile-production`,
`index.solrurl`, `autocomplete.solrurl`, `project.releaseVersion` from env), so no
post-hoc zip-patching:
```
docker compose run -T \
  -e FB_RELEASE=FB2026_02 -e FLYMINE_RELEASE=v1-2026-08 -e RC_NUMBER=1 -e COPY_PROFILE_DB=false \
  -e SOLR_INDEX_URL=http://172.31.59.87:8983/solr/flymine-search-v1-2026-08 \
  -e SOLR_AUTOCOMPLETE_URL=http://172.31.59.87:8983/solr/flymine-autocomplete-v1-2026-08 \
  flymine-builder /root/scripts/finalize_build.sh
```
(`COPY_PROFILE_DB=false` → profile resolves to the live `flymine_userprofile_test`,
which the entrypoint finds existing and does **not** touch. `db.production` resolves
to `flymine_v1-2026-08_rc1`.)

Then, on multitenant:
```
# backups first
cp /home/ec2-user/mine-wars/flymine.war /home/ec2-user/mine-wars/flymine.war.bak.rc3
docker run --rm -e PGPASSWORD=… postgres:15 pg_dump -Fc -Z6 -h <rds> -U postgres \
  -d flymine_userprofile_test > /home/ec2-user/flymine_userprofile_test_pre-v1cutover.dump
# swap + re-explode + restart
cp flymine-v1-2026-08-rc1.war /home/ec2-user/mine-wars/flymine.war
docker exec flymine sh -c 'rm -rf /usr/local/tomcat/webapps/flymine'   # force re-explode
docker restart flymine
```
> **pg_dump must be pg15** (RDS is 15.x) — a laptop pg14 client aborts on version
> mismatch. Use `docker run --rm postgres:15 pg_dump …`.

## Rollback

Everything for a rollback to rc3 is retained:
- `flymine.war.bak.rc3` on multitenant (`/home/ec2-user/mine-wars/`).
- `flymine_v0-2026-05-31_rc3` DB on RDS (intact).
- `flymine_userprofile_test_pre-v1cutover.dump` (pre-cutover profile snapshot).
- rc3's shared Solr cores untouched.

To roll back: `cp flymine.war.bak.rc3 → flymine.war`, `rm -rf webapps/flymine`,
`docker restart flymine`. If the bag upgrade mangled lists, `pg_restore -c -d
flymine_userprofile_test` from the dump.

Keep rc3 DB + WAR backup ≥ a few days, then drop `flymine_v0-2026-05-31_rc3` to
reclaim RDS.

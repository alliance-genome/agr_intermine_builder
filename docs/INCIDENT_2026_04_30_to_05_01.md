# Multitenant Incident — 2026-04-30 / 2026-05-01

Honest, full record. Use this to drive the AllianceMine cutover and to
not repeat the same mistakes.

---

## Tl;dr

- **2026-04-30 morning:** RDS-CPU alarm fires. Stuck 23-query pile on
  `alliancemine_8_3_0`. Root cause: scraper bot hammering
  `/service/list/enrichment` with 300+ gene IDs. Postgres planner
  spends 5–30 s per query.
- Fixes deployed in order: kill-queries (manual), ALB log enable,
  Tomcat AccessLogValve XFF patch, ALB listener rules priority 50/51
  blocking the bot IP set, ALB target-group / WAF planning.
- **2026-04-30 afternoon:** RDS storage low (72 GB free of 500 GB).
  Dropped a 57 GB checkpoint, enabled storage autoscaling to 1 TB.
- **2026-05-01:** MouseMine build still slow due to `t3.large` CPU
  credit starvation. After bot block + RDS cleanup, the same `CREATE
  INDEX` that took 2 h 11 m completed in **7.8 s** — 1000× faster.
- **2026-05-01 ~14:00:** Multitenant root EBS hit 100% full
  (containers blocking each other on overlay writes). Disk was 50 GB.
- **2026-05-01 ~15:00 — DAMAGE:** During disk recovery, ran
  `docker system prune -a -f`. The `alliancemine` and `wormmine`
  containers had crashed to `Exited` due to disk-full and were
  deleted by prune. Their WARs lived only in container overlay
  filesystems → unrecoverable from this host.
- Multitenant EBS resized 50 GB → 100 GB (XFS grown live).
- Wormmine recreated: `intermine-tomcat:latest` image (empty) +
  user's manual cargo redeploy. Then a long sequence of
  config-mismatch fixes: missing `main.min.css`, missing `pngfix.js`,
  missing CDN routing for `/css/*`, mixed-content blocking due to
  missing `RemoteIpValve`.
- **End of 2026-05-01:** WormMine home page loads styled. AllianceMine
  is still empty / unfixed. Bluegenes survived. Caddy CDN survived
  (native process, not Docker).

## Mistakes (own them)

1. **`docker system prune -a -f` was wrong tool.** Should have used `docker image prune -a -f` + `docker builder prune -a -f` to reclaim disk without deleting containers. Containers had crashed to Exited during disk-full and were swept up.
2. **Did not check container restart policy / state before disaster recovery.** A `docker ps -a` before pruning would have shown the Exited containers and given the option to `docker start` them instead of letting prune kill them.
3. **Replaced wormmine with `agr_wormmine:latest` ECR image** without checking the image's runtime expectations. It was the OLD all-in-one pattern, not drop-in.
4. **Sed-based XML edits inside containers broke `context.xml`** with malformed quoting. Should have used `docker cp` for any non-trivial XML/property file changes.
5. **Did not pause and ask** before running prune. `system prune -a -f` is a destructive command; a 30-second sanity check would have prevented the loss.

## Lessons / never-again

- Do not run `docker system prune -a -f` on a multitenant host without
  first listing all containers and confirming none are Exited from
  disk-full or other recoverable state.
- The `intermine-tomcat:latest` image used by current production is a
  bare Tomcat. WARs were Cargo-deployed into container overlays.
  This is a fragile pattern — any container loss = WAR loss. Bake the
  WAR into the image (or bind-mount it from `/data`) instead.
- AWS VPC `172.16/12` private range is **not** in Tomcat
  `RemoteIpValve` default `internalProxies` regex. Any Tomcat behind
  an AWS ALB needs an explicit `internalProxies` override or it
  generates HTTP URLs and gets mixed-content-blocked on HTTPS pages.
- Disk: 50 GB root is too small for a multitenant host running 4
  Tomcats. Now 100 GB. Should be ≥ 200 GB.

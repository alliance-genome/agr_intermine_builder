The crossReference gene count drops on purpose. In v1-2026-08, about 4.2K FBgns of human, mouse, yeast and
other non-Drosophila genes (genes named in transgenic constructs) had crossReferences while FlyMine labelled
them *D. melanogaster*. The extract now keeps only current genes of the 12 Drosophila species the chado
sources load (`docker/flymine/scripts/extract_gene_dbxrefs.sh`), which also avoids the ~145K stub genes the
September reload had to strip.

## How it was built

All on the build host (`/home/ec2-user/flymine-deploy/`), with `docker/flymine/scripts/build_release.sh`:

1. Merged build context (laptop scripts with the SES mail bake, plus build-host bio-sources) and rebuilt
   `flymine-builder:latest` (old image kept as `flymine-builder:fb2026_02-backup`).
2. New chado: `FB2026_03.sql.gz` (16.4 GB) restored into a fresh `chado-pg` (98,011,343 features, 0 errors, ~3.5 h).
3. `extract_data.py --all` with `FB_RELEASE=FB2026_03`, then `scripts/fix_flymine_data.sh`.
4. `run_builddb_v1_2026_10.sh` (guard: both properties files must target `flymine_v1-2026-10_rc1`).
5. Gene crossrefs from chado; 29-source integration (stops at the first failure); SQL patches;
   post-processing one step per JVM; finalize (summary, WAR, objectstoresummary injection, mail bake).

Deploy: WAR copied build host → laptop → multitenant (checksums matched), backups taken, `flymine.war`
overwritten in place, exploded `webapps/flymine` removed, `docker restart flymine` (up in ~10 s).

## Problems found and fixed during the build

| Problem | Fix |
|---|---|
| `docker-compose.yml` never passed `FB_RELEASE`, so `extract_data.py` silently fetched FB2026_01 | Pass-through added (75aca60) |
| The 4 Sep gap-fill bio-sources existed only on the build host | Saved to `new_flymine/flymine-bio-sources` branch `agr/flymine-gapfill-sources` (3211075) |
| WARs shipped without mail settings (hand-patched after every deploy) | `mail.*` block + `MAIL_*` pass-through; mail fix baked in |
| The image bakes `/solr/flymine-search` into the dbmodel resources | `build_release.sh` points them at the per-release cores in every step |
| `grep` read commented-out post-process steps (`populate-child-features`) | XML parse (6614c71) |
| The WAR was built inside a `--rm` container and lost | Copied to `data/wars/` (c98409e) |
| Homologues fell from 481K to 35K rows: September's hand-staged paralog file | `fix_flymine_data.sh` stages `dmel_paralogs_<rel>.tsv` for `drosophila-homology` (c98409e) |
| Shared RDS at 99.9% CPU for days (14 stuck MM 5.1 test-DB counts + a 26-day temp-table query on rc3) | Terminated; `statement_timeout=10min` on `mousemine_im5_test` |

## Rollback

On multitenant: `cp /home/ec2-user/mine-wars/flymine.war.bak.v1-2026-08-rc3 /home/ec2-user/mine-wars/flymine.war`,
`docker exec flymine rm -rf /usr/local/tomcat/webapps/flymine`, `docker restart flymine`. The rc3 database and
the `-v1-2026-08` Solr cores are unchanged. If lists were damaged by the bag upgrade, restore
`~/flymine_userprofile_test_pre-v1-2026-10.dump` on the build host with pg15 `pg_restore -c`.

Keep the rc3 database and WAR backup for at least a week. Release the FB2026_02 FlyBase data
(`data/flybase.fb2026_02`, 18 GB) on the build host after that.

## 1. MouseMine 5.1 port

Repos (private, nuin): `mousemine-im5` (the mine) and `mousemine-bio-sources-im5`, both pushed.
Full comparison with 1.8: report artifact <https://claude.ai/artifact/QBjchBuQV8nFx4W8q5LCzP> and
`docs/IM5_PORT_GAP_INVENTORY.md` in `mousemine-im5`.

**Build.** Test database `mousemine_im5_test` (plus `_items` and `_userprofile`), built on AllianceMineDev
with `scripts/im5_test_build.sh`, from the same MGI ETL release as production 1.8 (2026-08-24).

- All 58 sources and 10 post-processes ran. 118 of 129 classes match 1.8 row for row; the total is −0.1%.
- Things 5.1 needed that 1.8 didn't:
  - InterMine 5.1.0 bug patches (in `patches/`):
    - `PostgresDataOutputStream` (NUL characters);
    - `ObjectStoreFastCollectionsForTranslatorImpl` (a re-executed load batch referenced objects that were never stored);
    - `CreateChromosomeLocationsProcess` (ran out of RDS lock memory; now commits every 50k);
    - `Protein2iprConverter` (NCBIfam ids).
  - `project.xml` renames for 5.1: `location=` paths, `mgi-fasta.*` properties, `osAlias`, an absolute
    output path for update-publications, and the gene-ID resolver file for psi-intact.
  - Solr URLs live in `keyword_search.properties` / `objectstoresummary.config.properties` in 5.x.
  - Post-processing runs **one JVM per step**. In a single JVM each step leaked a 20-connection pool
    and exhausted the shared RDS on 2026-09-26 (production mines were locked out from about 07:15 to 07:50 UTC).
- Data differences from 1.8:
  - Panther homologues −6.7% (the 5.1 loader resolves gene IDs);
  - author names now keep accented characters (1.8 had 33,656 names with `?` in place of them);
  - 1,304 junk ontology cross-reference terms;
  - the model renames `Publication.bioEntities` → `entities` and `Strain.genome` → `features`, and
    changes `Organism.taxonId` to text.

**Deploy on multitenant** (internal: `http://172.31.59.87:8088/mousemine/`):

## 3. MouseMine 1.8 (production)

**Six-day outage, 2026-09-22 to 09-28.** The JVM ran out of heap (bot-style template crawls). The
container stayed "Up", so nothing restarted it, and the ALB just marked the target unhealthy.
Restarted 2026-09-28 14:01 UTC.

**Model-browser counts.** They came from a summary file baked into the WAR in May, which was never
regenerated when production was switched to the August data (`mousemine_rc4`). QueryBuilder showed,
for example, 808,036 alleles against a real 823,414. The summary was regenerated for rc4 in the 1.x
build container and installed; the May file is kept as `objectstoresummary.properties.bak.2026-05-05`.

**Restart outage and fix (2026-09-29).**
- Upstream 1.x `KeywordSearch` deletes and re-extracts the whole keyword index from the database
  on every JVM start: 1.2 GB zipped, 6.5 GB on disk.
- It does this inside a synchronized method, so every search blocks. All 200 Tomcat threads filled
  and the site was down 13:45–16:14 UTC, then search failed with OutOfMemoryError.
- Patch `patches/mousemine-1x/KeywordSearch.java` (cf8aac5): reuse the on-disk index when its
  `.index-source` marker names the index stored in the database and every file size matches;
  otherwise extract as before, with 1 MB reads.
- Deployed with `deploy_keyword_patch.sh`: heap 6 GB, container limit 8 GB, `ExitOnOutOfMemoryError`.
- Result: a restart now takes about 10 s. It reused the index again after the resize.
- A **new release** (new index in the DB) still does one full extraction, so warm it outside working hours.
- Details: `docs/MOUSEMINE_1X_KEYWORD_INDEX_FIX.md`.

**www.mousemine.org.** The ALB has no fixed IP, and our certificate covers only `*.alliancegenome.org`.
MGI keeps their DNS and redirects from their Apache server to `https://mousemine.alliancegenome.org/…`
(root to `/mousemine/`, paths and query strings kept). A CNAME later would need an ACM certificate for
`www.mousemine.org`, which needs someone with ACM rights; my IAM user can't request one.

## 4. Multitenant resize (2026-09-30 00:37–00:54 UTC)

- `c7i.4xlarge` (16 vCPU / 32 GB) → **`r7i.2xlarge` (8 vCPU / 64 GB)**. CPU had peaked at 16%, and the
  hourly price is lower.
- Script `scripts/resize_multitenant.sh`: preflight baseline, then stop, snapshot, change type, start
  and verify against the baseline.
- Snapshots: `snap-0e342f558a6dea8f8` (root), `snap-0ceb298481f66b4d5`.
- Every mine and all 8 ALB target groups matched the baseline afterwards. Downtime was about 15 minutes.
- The public IP changed from `44.206.248.213` to **`98.94.35.110`** (not an Elastic IP); no DNS
  record used it.
- Before the resize, `wormmine` and `alliancemine` were set to restart policy `unless-stopped`; they
  had `no`, which would have left WormMine down after the stop/start.
- While checking the host, I found the `alliancemine-9.0.0-rc20` container on :8086 **is the live
  AllianceMine 9.1.0**. Its name is out of date; never retire it by name.

## 5. YeastMine

**Weekly build + automatic deploy** (`docker/yeastmine/weekly/`, runbook `docs/YEASTMINE_WEEKLY_BUILD.md`):
- Build: Fridays 22:00 America/Los_Angeles on AllianceMineDev.
- Checks against the live build before anything is published.
- Deploy: on multitenant, every 30 minutes, via S3. It swaps the Solr cores and the WAR, verifies the
  site, and rolls back automatically on failure.
- Keeps the newest 4 builds.
- The deploy agent was installed 2026-09-30. The first run is Friday 2026-10-02.

**Release label.** The header and `service/version/release` show
`R64-5-1 (built <Pacific date>, GO <GO release>)`. Production now shows
`R64-5-1 (built 2026-09-02, GO 2026-07-26)`, set by hand for rc3; weekly builds set it automatically.

**Logo.** `service/branding` pointed at `yeastmine.yeastgenome.org`, which no longer answers, so
BlueGenes showed no logo. It now uses our copy, in production and in the build template (d97063e).

**Found and fixed along the way:**
- Production's Solr index dated from June (rc1). The weekly build reindexes every week.
- The WAR shipped empty mail settings; production only worked because of a hand edit. `MAIL_*` is now
  in the build `.env`, and the mail fix is baked into every WAR.
- `os.query.max-time` had been hand-set to 3,600,000, below InterMine's default, which breaks
  enrichment widgets. Weekly builds restore the documented 500,000,000.

**Still open:** the "BlueGenes" link in the classic header goes to `bluegenes.yeastgenome.org`, which returns 503.

## 7. FlyMine

Keyword search returned 500 for every query. The WAR's Solr cores dated from the rc1 build
(2026-08-26), but production was switched to rc2 (09-07) and then rc3 (09-10), whose reloads changed
object IDs.
- Reindexed from `flymine_v1-2026-08_rc3` into the empty standby cores
  (`docker/flymine/scripts/reindex_search.sh 3 v1-2026-08-rc2`, one JVM per step, about 6 minutes).
- Then a Solr `SWAP` with the live `*-v1-2026-08` cores. No restart was needed.
- The live index now has 3,717,288 documents. The old index is in the `-v1-2026-08-rc2` cores
  (swap again to roll back).
- **Rule:** switching FlyMine to a new database must include a reindex.

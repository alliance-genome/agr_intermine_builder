InterMine build workflow
Comparison & operator guide

A practical review of the move from a Python orchestration stack to a small launcher over Docker Compose and the existing mine pipelines.

This document describes the committed implementation at the revision above. It is self-contained for reading offline. Source links work when the file remains in the repository. Examples are instructions for an operator; opening this document executes no build commands.

1. What changed

The new entry point is ./mine. It chooses a mine directory, invokes Docker Compose or an existing build script, captures output for build commands, and returns the command's result. Docker Compose owns container settings. Each mine's pipeline owns its stages.

./mine alliancemine image
./mine alliancemine build --skip-stages deploy
./mine alliancemine shell
./mine alliancemine logs -f

Previously, the repository offered two routes to a build: a generic Python CLI with its own configuration and stage engine, and the Compose-based workflows already described in the mine runbooks. The refactor retires the generic engine and makes the existing Compose path the common entry point.

The reduction is in host orchestration. The old CLI and five build/configuration modules totalled 2,050 lines. The new launcher module is 155 lines, with a small executable and compatibility alias. These figures exclude mine pipelines, operational tools, tests, and documentation; the refactor does not imply faster data integration or lower memory use.

The Dockerfiles, extraction logic, database protection, production promotion, and deployment rollback remain in their existing components. The installed build-mines command remains an alias, but it accepts the new command syntax. The former Python build API is removed.

For someone already running docker compose directly, the change is mainly a shorter entry point and persistent host output. For someone using the old MineBuilder API, it is an intentional interface and configuration migration.

Evidence: launcher, baseline modules, and implementation record.

2. Architecture before and after

Previous Python route

  1. build-mines build --mine …Parse the generic build interface
  2. Config + MineConfigLoad host configuration and a separate mine registry
  3. MineBuilderCreate a network, image, and container; track the build
  4. BuildExecutor + DockerManagerSchedule stages and execute them through the Docker SDK
  5. Container commandsGradle, extraction, integration, and deployment

Alongside this route, operators could already run the Compose projects and mine-specific scripts directly.

Current common entry point

  1. ./mine MINE ACTIONSelect a directory and preserve command arguments
  2. Compose or an existing host scriptRead the selected project's settings; invoke the mine's own pipeline
  3. Container entrypoint and toolsPrepare properties and databases; run the requested work

AllianceMine's pipeline runs inside its container. FlyMine and YeastMine use host scripts that issue their own Compose commands. The launcher does not recreate their stage logic.

Where the commands run

Normally, you SSH to the build machine, enter the checkout, and run ./mine. The launcher has no SSH transport or remote-job service. Docker uses the CLI's configured context. RDS, Solr, source databases, S3, and the runtime host remain external systems accessed by the existing scripts.

The build machine creates images and runs integrations. The runtime host serves Tomcat and Solr. Running the launcher does not install or update a remote deploy agent, alter a timer, or synchronize a second checkout.

4. A first build, step by step

This example is for an already provisioned AllianceMine build machine. Replace the sample release and RC with your intended candidate. Configure external services according to the release runbook before starting integration.

  1. Connect and inspect the checkout.
    ssh build-host
cd /path/to/agr_intermine_builder
git branch --show-current
./mine list
docker compose version

    Review this branch separately from the existing production workflow. A Docker CLI configured for another context operates on that context; verify the machine and daemon you intend to use.

  2. Configure the selected mine.
    # On first setup only; preserve an existing .env.
cp docker/alliancemine/.env.example docker/alliancemine/.env

    Edit the file locally with RDS, SGD, Solr, and release settings. The persistent alliancemine_userprofile database must already exist. Credentials remain in the untracked configuration.

  3. Preview, then build the image.
    ./mine --dry-run alliancemine image
IMAGE_TAG=review1 ./mine alliancemine image

    The preview prints a directory and command. It does not contact Docker or validate services. The image build uses the selected Dockerfile and its configured sources.

  4. Run the data build in a durable terminal session.
    tmux new -s alliancemine-review
ALLIANCE_RELEASE=9.0.0 RC_NUMBER=21 BUILD_TYPE=test IMAGE_TAG=review1 \
  ./mine alliancemine build --skip-stages deploy

    The explicit skip keeps this example out of the deployment stage. The entrypoint configures the target database before the pipeline starts; review the printed target before destructive schema work.

  5. Observe from another terminal.
    ./mine alliancemine status
./mine alliancemine logs -f

    Use the exit status of the original build command to determine success. A removed one-off container will no longer appear in status. The host output file remains.

  6. Preserve the output you need.

    Database changes live in RDS, and mounted data lives on the host. Files written elsewhere inside a --rm container disappear with it. Confirm WAR export before concluding that a build-only run produced a reusable release artifact; see logs and artifacts.

5. Complete command reference

./mine [--directory DIR] [--dry-run] MINE ACTION [ARGS...]
./mine list

Place launcher options before the mine name. Everything after the action is passed to the selected command, except for the host-build argument checks described below. Mine names are alliancemine, flymine, mousemine, wormmine, and yeastmine.

ActionDispatchOperational behavior
listPrint the five supported names.No Docker invocation or configuration lookup. Use without an action.
imagedocker compose … build [ARGS] MINE-builderBuild the selected service image; append output to the host log. Build flags such as --no-cache pass through.
buildAllianceMine container pipeline, FlyMine host release script, or YeastMine host weekly script.Append output to the host log. MouseMine and WormMine return an error because these directories have no full pipeline.
rundocker compose … run --rm -T MINE-builder [ARGS]A fresh non-TTY container runs your command; the existing entrypoint executes first. At least one command argument is required. Output is logged.
shelldocker compose … run --rm MINE-builder bash [ARGS]Interactive shell after entrypoint setup. Output is not appended to the launcher log.
statusdocker compose … ps --all [ARGS]Inspect container state, including stopped containers that still exist. No pipeline history is reconstructed.
logstail -n 100 [ARGS] DIR/logs/commands.logRead host output; Docker and the Compose file are not needed. Use -f to follow. A missing file produces a normal tail error.
composedocker compose … [ARGS]Explicit passthrough for services, exec, inspection, and maintenance. No launcher log capture; the requested Compose command determines side effects.

For direct Compose actions, the ellipsis above is --project-directory DIR -f DIR/docker-compose.yml. The launcher also changes its working directory to DIR. Host pipelines use their own Compose invocations after entering the selected directory.

Examples and argument boundaries

./mine --directory "/srv/builds/alliance candidate" --dry-run alliancemine image
./mine alliancemine run python3 /root/scripts/extract_data.py
./mine mousemine run bash -c 'cd /root/mousemine && ./gradlew :dbmodel:assemble'
./mine flymine compose exec -T chado-pg psql --version
./mine alliancemine logs -n 25
./mine alliancemine status --format json

Arguments are preserved as an argument list. The launcher does not interpret a supplied semicolon or dollar expression as shell syntax. If you intentionally need shell expansion, request bash -c and quote that command yourself.

Installed entry points

# Optional: needed for installed entry points and operational-tool dependencies.
uv pip install -e .

mine --directory /srv/builds/alliancemine alliancemine image
build-mines --directory /srv/builds/alliancemine alliancemine image
python -m src.cli.build_mines list

The aliases lead to the same launcher. They do not preserve build --mine …, stage, cleanup, or build-all. A wheel contains the Python commands, not a copy of the Docker build contexts; provide --directory when using an installed wheel outside a checkout.

6. Configuration and paths

The selected directory is the starting point

By default, the checkout launcher resolves docker/MINE/ relative to its own source location, not your terminal's current directory. --directory selects an existing mine directory elsewhere. This is useful when a build machine has a prepared deployment tree with its own data and source files.

./mine --directory /home/ec2-user/flymine-deploy flymine build

The selected directory must contain docker-compose.yml. The host-build actions also require their build script inside that directory. Selection does not copy files, stage a fork, install checks, or update an older deployment tree. FlyMine's selected script must include support for FLYMINE_DIR to honor an alternate path.

SettingWhere it belongsWhat the launcher does
RDS / external-source credentialsThe selected mine's untracked .env and the existing tool-specific configuration.It inherits the process environment. It does not parse a credential file or apply the old POSTGRES_*/DB_* fallback rules.
Image name / resource limits / mountsThe selected Compose file, including its environment substitutions.It delegates to that file. It does not override limits or translate old named volumes.
Release and candidateMine-specific release variables, BUILD_TYPE, and RC_NUMBER before container startup.It leaves database naming to the entrypoint.
FlyMine build location--directory.It sets FLYMINE_DIR for the host script.
YeastMine build location--directory.It sets YM_DIR. Other paths such as WEEKLY and AMFMS retain their script-defined behavior.

Direct Compose actions use Compose's environment interpolation. FlyMine and YeastMine host scripts additionally source their .env as shell code. Values assigned there can overwrite inherited shell values; ensure the file and invocation agree. There is no new universal environment-precedence layer.

Pin identity before startup

ALLIANCE_RELEASE=9.0.0 RC_NUMBER=21 BUILD_TYPE=test \
  ./mine alliancemine build --start-from project_build --resume --skip-stages deploy

For this AllianceMine example, the entrypoint derives alliancemine_9_0_0_rc21, configures properties, and verifies the persistent profile database before dispatching the build. A fresh invocation without a pinned RC can allocate another candidate.

Pipeline flags arrive later than entrypoint configuration. The launcher currently forwards flags such as --rc, --release, and --build-type; it does not reject or synchronize them. Use the corresponding environment settings before startup rather than changing the target only in pipeline arguments.

What dry run proves

--dry-run validates the selected command shape and required local paths, then prints the working directory and command. It starts no process and creates no log. It does not render the full effective Compose configuration, query RDS, check Docker availability, resolve credentials, or show every inherited environment value. Host-script directory overrides are applied during real execution even though the preview only prints the command and working directory.

7. Images, tags, and publishing

An image build assembles the container environment and code. A data build starts that image and performs integration against databases and mounted data. Those are separate operations in the new interface.

IMAGE_TAG=review1 ./mine alliancemine image
docker image inspect alliancemine-builder:review1
IMAGE_TAG=review1 RC_NUMBER=21 \
  ./mine alliancemine build --skip-stages deploy

image allows Docker's normal build cache. Use image --no-cache only when you want a cache-free rebuild. The old --rebuild forced the SDK to call image build again; it did not itself request a cache-free Docker build. The closest routine replacement is a separate image command, followed by build.

FlyMine and YeastMine source staging

Their Dockerfiles depend on prepared local source trees. Their existing helper stages those trees and builds an amd64 image. Configure the source-directory environment variables documented at the top of each helper.

(cd docker/flymine && ./scripts/build_and_push.sh --no-push --tag review1)

# From the repository root, use the resulting local image:
IMAGE_TAG=review1 ./mine flymine shell

The subshell keeps your terminal at the repository root. The corresponding YeastMine helper lives under docker/yeastmine/scripts/. These helpers are separate from ./mine … image; the launcher does not automatically run their source-copy steps.

Publishing stays explicit

The existing helpers publish to ECR when --no-push is omitted and may create the configured ECR repository. Review their ECR_ACCOUNT, ECR_REGION, ECR_REPO, and tag settings before using that mode. For other images, use the established Docker tag/login/push workflow.

The builder Compose files use local image names by default. A tag selection alone does not configure a registry destination. Image publication, pulling onto another machine, and selecting the image for a build remain distinct steps.

Evidence: Compose image definitions and source staging / ECR helpers.

8. Workflows for all five mines

The interface is shared, but the build processes retain their differences. “Supported” below means the launcher has a delegation path; it does not mean a live build was executed during this refactor.

AllianceMine

Full container pipeline

build invokes the container's existing build command. Its stage names are buildDB, extract_data, project_build, postprocess, war, and deploy. The entrypoint resolves the release/RC, renders properties, prepares main/items databases, and requires the existing shared user-profile database.

# New candidate, with deployment excluded.
ALLIANCE_RELEASE=9.0.0 RC_NUMBER=21 BUILD_TYPE=test \
  ./mine alliancemine build --skip-stages deploy

# Resume that candidate's integration checkpoint.
ALLIANCE_RELEASE=9.0.0 RC_NUMBER=21 BUILD_TYPE=test \
  ./mine alliancemine build --start-from project_build --resume --skip-stages deploy

# Continue at indexing after integration already completed.
ALLIANCE_RELEASE=9.0.0 RC_NUMBER=21 BUILD_TYPE=test \
  ./mine alliancemine build --start-from postprocess --skip-stages deploy

--resume changes the integration command to project_build -l. It is not a generic checkpoint manager for every stage. Verify that the expected candidate and checkpoint exist. Solr setup remains the pipeline's existing preflight, including its current nonfatal failure handling.

--skip-stages deploy is explicit because the existing pipeline retains its deployment stage. The entrypoint can default the deployment host to localhost; an unset host is not a reliable substitute for skipping deployment.

FlyMine

Existing host release pipeline

build calls scripts/build_release.sh under the selected directory and supplies FLYMINE_DIR. The pipeline expects a prepared build database, release settings, mail configuration, Solr cores, Chado restore state, local source, and its data/integration scripts.

./mine --directory /home/ec2-user/flymine-deploy flymine build

RESUME_AT=postprocess \
  ./mine --directory /home/ec2-user/flymine-deploy flymine build

Its stage keys are data, xrefs, integrate, sqlpatch, postprocess, and finalize. It accepts resume through environment variables, not launcher build arguments. The wrapper rejects extra build arguments rather than allowing the script to ignore them.

Detailed logs remain under logs-$FLYMINE_RELEASE/; the launcher captures the script's emitted summary. The existing script currently names /root/data/full_integrate_v1_2026_10.sh and carries host-specific Solr assumptions. Those must be reconciled when preparing another release or a fork.

YeastMine

Existing weekly pipeline, publication disabled

build calls weekly/weekly_build.sh --no-publish and sets YM_DIR to the selected directory. The installed check script at $WEEKLY/bin/check_build.py, standby Solr cores, live manifest, mail settings, and source-data paths must already be available.

./mine yeastmine build
RESUME_RC=21 ./mine yeastmine build

Resume requires the candidate to exist and contain data, rejects the live database, and continues at the search-index steps. It skips extraction and integration; it does not behave like AllianceMine's --start-from.

“No publish” still performs a real build. It writes databases and standby indexes, uploads status, runs validation, and applies the existing retention policy to older candidates, local WARs, and S3 artifacts. It suppresses publication of the new WAR/ready manifest; it is not a read-only test or dry run.

The scheduled build timer and runtime deploy agent retain their existing publishing workflow. The launcher does not replace installed copies or change their schedules. Do not run a manual build concurrently with an incompatible scheduled run; the existing weekly lock remains owned by that script.

MouseMine

Individual commands

This repository's Compose directory has no full build script. ./mine mousemine build exits with guidance to use run. This limitation describes the in-repository builder, not every separately deployed MouseMine system.

./mine mousemine image
./mine mousemine shell
./mine mousemine run bash -c \
  'cd /root/mousemine && ./gradlew :dbmodel:assemble --stacktrace'

Prepare the data paths and source configuration described in the mine-specific runbook before integration. A successful model compilation is not a completed data build.

WormMine

Individual commands

WormMine also has no full pipeline in its Compose directory. The existing image supplies build tools and the WormBase fetch helper; it expects prepared data and a valid source configuration for integration.

./mine wormmine image
./mine wormmine run /root/scripts/find_and_copy_wormbase_files.sh /root/data/wormbase
./mine wormmine shell

Use WORMBASE_RELEASE and the existing branch/configuration settings. The launcher does not infer an integration order or reuse AllianceMine stages for WormMine.

Evidence: AllianceMine, FlyMine, YeastMine, and MouseMine / WormMine.

9. Logs, artifacts, and failures

Persistent launcher output

image, build, and run append a timestamp/action heading plus both command output streams to DIR/logs/commands.log. Repeated commands append to the same file. The launcher adds no rotation, per-run JSON manifest, duration report, or final exit-status record.

./mine alliancemine logs
./mine alliancemine logs -f
./mine --directory /srv/builds/yeastmine yeastmine logs -n 50

Use the command's returned status in automation. A pipeline's own log files or manifests can contain additional stage information. Commands launched with shell or the raw compose action do not automatically appear in commands.log. Concurrent logged commands can interleave output.

Where results survive

OutputPersistenceOperator implication
RDS databases and checkpointsExternal to the build container.A failed or cancelled run can leave partial data and checkpoints. Follow the mine's recovery procedure.
/root/dataMounted from the selected Compose project's data directory.Validate that this is the expected host data, especially when migrating from old named volumes.
Launcher stdout/stderrDIR/logs/commands.log.Survives one-off container removal. This is not a copy of every file written inside the container.
FlyMine / YeastMine WARsTheir existing finalization scripts copy WARs into mounted data/wars/.Check the expected filename and downstream validation; publication remains separate.
AllianceMine / individual Gradle WARsA WAR under webapp/build/libs/ is normally inside the disposable container.The launcher does not export it. Copy it to a mounted location in the same invocation if deployment is deferred.
Other container-local filesLost when a --rm container is removed unless mounted or copied out.Do not expect a later run to reuse the previous container's filesystem.

For example, when building a MouseMine WAR separately, preserve it before that container exits:

RC_NUMBER=21 ./mine mousemine run bash -c '
  set -e
  cd /root/mousemine
  ./gradlew :webapp:war --stacktrace
  mkdir -p /root/data/wars
  cp webapp/build/libs/webapp.war "/root/data/wars/${RDS_DB_NAME}.war"
'

The analogous AllianceMine export can run its full pipeline and copy the resulting WAR within one run bash -c invocation, or use an explicitly managed Compose container. Choose and verify the intended WAR file before deploying. A later container should not assume the previous container's build directory exists.

Exit codes and cancellation

The logging pipeline uses Bash pipefail. A failed build or a failed tee operation returns a failure. Invalid/unsupported launcher invocations return 2; launcher filesystem/exec failures return 1. The wrapper converts signal termination of its logged shell into the conventional 128 + signal status when that shell exits by signal.

For logged commands, SIGINT, SIGTERM, and SIGHUP sent to the launcher are forwarded to the owned command process group. Direct-PID cancellation and terminal Ctrl-C were tested with local stand-ins. Actual Docker daemon/container cancellation still requires a build-host check. Cancellation is not a database rollback; inspect container and database state before resuming.

if ./mine alliancemine build --skip-stages deploy; then
  echo "Pipeline completed; inspect the candidate and retained artifacts."
else
  result=$?
  echo "Build failed with status $result; inspect the logs." >&2
  exit "$result"
fi

10. Deployment and rollback

The launcher simplifies starting a build. Production cutover still follows the existing release and promotion procedures. A successful integration does not by itself confirm a deployable WAR, correct Solr targets, a healthy runtime, or a completed production cutover.

OperationCurrent ownerReview requirement
AllianceMine deploymentThe existing pipeline deploy stage and WAR/release scripts.Keep --skip-stages deploy on build-only invocations. Use the release runbook to select the runtime and retain the artifact.
Database promotionpromote_db.py and promote_to_production.py.The occupied-target protection from the earlier fixes remains. Archive/prepare an existing production target using the promotion protocol before retrying.
YeastMine publishingThe existing scheduled/explicit host-script workflow.The launcher's manual build always uses --no-publish. Its raw Compose action does not provide a universal publish command.
YeastMine deployment and rollbackThe existing runtime deploy agent.WAR checks, completed-core-swap tracking, restoration, and ROLLBACK_FAILED reporting remain in that agent.
RDS administrationrds-manager / src.cli.rds_manager.Independent administrative command. The refactor also corrected status to use its selected-profile client; it did not redesign the other administrative commands.
Release and database utilitiessrc.cli.set_release, src.cli.db_admin, and operational scripts.Retain their existing configuration and behavior. Review the selected mine's actual .env rather than assuming a utility updated every project.

The production-protection and extraction/rollback fixes were already present at comparison baseline 829d28b. They are carried forward, not new features of the launcher. The launcher introduces no automatic production-database migration and no cross-system transaction around a build.

Operational references: release process, promotion protocol, YeastMine weekly/deploy runbook, and host tools.

Calling the launcher from Python

import os
import subprocess

subprocess.run(
    ["./mine", "alliancemine", "build", "--skip-stages", "deploy"],
    cwd="/path/to/agr_intermine_builder",
    env={**os.environ, "ALLIANCE_RELEASE": "9.0.0", "RC_NUMBER": "21"},
    check=True,
)

The caller receives a normal process outcome. If it needs stage-level status or an artifact manifest, it must consume the particular pipeline's outputs or add that capability deliberately. The launcher does not supply the old dictionary-returning API.

Removed and retained files

The five removed modules are mine_builder.py, docker_manager.py, build_executor.py, mine_config.py, and config.py. Their obsolete unit tests and Python API example were removed. The old build CLI module is now a small alias.

The package drops Docker SDK and dotenv dependencies. Installing the full package still installs its operational-tool dependencies, including boto3, psycopg2, and requests. The dependency-free claim applies to running the checkout launcher, not to every tool in the repository.

AGENTS.md was preserved as requested; its older orchestration description is historical on this branch. The root README and current build-system guide describe the new behavior.

12. Adoption and a future fork

The implementation was committed locally on simplify-compose-launcher. It was not pushed, merged, deployed, or used for a live integration during the refactor. Use a separate checkout for build-host evaluation if you want to preserve the existing operational checkout.

  1. Inventory current callers and storage.

    Identify timers, CI scripts, operator commands, and external Python consumers. Record the Compose directory, data mounts, image tags, active database names, profile database, and artifact locations for each mine.

  2. Prepare the branch without moving live data.

    Bring the reviewed commit into the chosen checkout. Supply its mine-specific .env files and required scripts through the existing operational process. Compare old named volumes with the intended host data directories; decide how data will be reused before changing mounts.

  3. Check paths and inspect state.
    ./mine list
./mine --dry-run alliancemine image
./mine --dry-run alliancemine build --skip-stages deploy
./mine alliancemine status

    Dry runs are local previews. Status reaches the selected Docker daemon. Neither validates a candidate build's data completeness.

  4. Exercise one prepared candidate.

    Pin the release/RC and image. Verify configured resource limits, source access, log retention, artifact export, and cancellation against a disposable candidate. Compare the expected row counts, Solr output, and WAR configuration before considering production adoption.

  5. Migrate callers deliberately.

    Replace old syntax and Python API calls. Use a shell script or scheduler only for the pipelines you intend to run. Update an installed weekly-script copy or timer separately if that is part of the approved operational change.

  6. Promote through the existing process.

    Use the release runbooks for candidate acceptance, production promotion, deployment, verification, and rollback. A code-branch switch does not reverse database mutations, S3 uploads, or index changes.

If this becomes a fork

This branch provides a clear starting point for a smaller build-tools repository. Before publishing a fork, review hardcoded host paths, Solr endpoints, ECR defaults, upstream source URLs, release-specific scripts, and deployment assumptions. Keep credentials external and preserve the repository's license and attribution requirements.

Decide whether the fork should retain the RDS/maintenance tooling and historical runbooks or focus on builders. That split has not been performed here. Reusing this branch does not require introducing another generic stage engine or rewriting the existing biological data pipelines.

Those actions were not run as part of this refactor.

14. Limitations and review decisions

The main tradeoff is explicit delegation: the command surface is smaller, while the mine pipelines keep their existing responsibilities and assumptions. These are the decisions to review before adopting the branch.

Current boundaryQuestion for review
No generic build API or build-all schedulerDo any external callers need a migration path beyond subprocess invocation and normal exit codes?
No shared stage/resume modelAre the existing AllianceMine flags, FlyMine environment controls, and YeastMine resume behavior clear enough for operators?
MouseMine / WormMine full builds are unavailable in these directoriesIs command-level access sufficient now, or should a later project add explicit mine-owned pipelines?
Artifact export remains pipeline-specificShould a follow-up standardize retained WARs and manifests, especially for AllianceMine build-only runs?
No launcher-wide concurrency guardWhich builds may run together, considering memory, shared items databases, Solr targets, and existing pipeline locks?
One append-only output file per selected directoryIs a simple log sufficient, or are per-run logs, rotation, and a machine-readable result worth adding later?
Target identity is configured before pipeline argumentsShould a follow-up reject conflicting target flags rather than relying on the documented environment-based convention?
Host scripts retain local assumptionsWhich paths, release-specific assets, and registry defaults must be parameterized before a fork or another build machine?
